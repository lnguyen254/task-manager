# Day 4 — Frontend scaffold + auth wiring: Summary

Status: Complete. All 9 steps from `plans/day-4-frontend-scaffold-auth.md` executed and verified.

## What was done

1. **shadcn/ui installed and configured.** Tailwind v4 was already set up on Day 1, so this step was just `shadcn init`. The installed generation (`shadcn@4.13`, `base-nova` style) is a newer architecture than the classic Radix-based shadcn/ui — components are built on `@base-ui/react` primitives, not Radix, and there's no bundled `Form`/`FormField` wrapper (confirmed via the CLI's own `view`/`docs` commands: the `form` registry entry is an empty stub). Both facts shaped later steps rather than being worked around.

2. **Base layout built.** Added `SiteHeader` (brand link + nav), wired it into the root layout with a consistent `<main>` shell, and replaced the `create-next-app` boilerplate homepage with real content. Caught and fixed a real bug while verifying: `globals.css`'s `@theme inline` block mapped `--font-sans` to itself (an undefined variable) instead of `--font-geist-sans`, so the whole app was silently falling back to a generic serif — confirmed via `getComputedStyle` before/after the fix, not just visually. Nav links use `buttonVariants()` classes on plain `<Link>`s rather than `<Button render={<Link/>}>`, since Base UI's own docs explicitly warn its `Button` enforces button semantics and shouldn't wrap anchors.

3. **`web` added to `docker-compose.yml`.** New `apps/web/Dockerfile` mirroring the Day 1 `apps/api/Dockerfile` pattern. Caught the same class of bug Day 1 already fixed once for the API image: the first version's `CMD ["pnpm", "start"]` silently triggered a full pnpm workspace reinstall over the network on every container start (`Scope: all 2 workspace projects` in the logs). Fixed by invoking the built `next` binary directly — confirmed cold start dropped to 163ms with zero network calls.

4. **BFF auth proxy Route Handlers.** `/api/auth/{register,login,refresh,logout}` forward to the NestJS API and translate the response into httpOnly cookies — the browser never sees a raw token. Read the actual backend source (controller/DTOs/service) rather than assuming the contract: `register` returns no tokens (so its route handler auto-logs the user in via a chained `/auth/login` call), `login`/`register` return **201** not 200, and `refresh`/`logout` take `refreshToken` in the body, not a header. The `secure` cookie flag is derived from the incoming request's actual protocol rather than hardcoded or tied to `NODE_ENV` — a hardcoded `true` would make Chrome silently drop the cookie over the plain HTTP used for all local/Docker testing, breaking login outright. Verified live against the real Dockerized API: register/login/refresh-rotation/logout, plus error passthrough (409 duplicate email, 401 wrong password, rejected reuse of a rotated or logged-out refresh token).

5. **Login page.** `react-hook-form` + Zod, plain `Input`/`Label` primitives with manual `register()` wiring (no `Form` component exists in this shadcn generation, see step 1). `@hookform/resolvers`'s `zodResolver` failed to type-check against the installed Zod 4.4.3 (its types are pinned to an older internal Zod version stamp); switched to the version-agnostic `standardSchemaResolver`, which Zod v4 supports natively. Also created a minimal `/dashboard` placeholder as the login redirect target, since no authenticated page existed yet. Live browser testing caught a real UX bug — a stale server-error banner stayed on screen if a client-side validation error happened afterward, because the handler that clears it never ran when Zod blocked the submission — fixed with `handleSubmit(onSubmit, onInvalid)`.

6. **Register page.** Same pattern as login, with password-length helper text that gets replaced by the Zod error (not shown alongside it). Pulled the duplicate `extractErrorMessage` helper out of the login form into `lib/utils.ts` rather than letting a second copy exist. Verified live: registration → auto-login → `/dashboard`, duplicate email forwarded as 409, sub-8-character password blocked client-side with zero network calls.

7. **Session handling.** Two-tier design, driven by a real constraint: Server Components can read cookies but not write them, so a Server-Component-safe session check can't perform a token refresh. `getCurrentUser()` (`lib/session.ts`) is the read-only version used by `SiteHeader` and `DashboardPage`; `/api/auth/me` is the fuller Route Handler version that *can* refresh-and-retry when the access token is missing or expired, for client-side use. Added `proxy.ts` — Next.js 16 renamed `middleware.ts`/`middleware()` to `proxy.ts`/`proxy()`, confirmed from the framework's own bundled docs — for an optimistic cookie-presence redirect ahead of the authoritative server-side check. Making the header auth-aware has a real, permanent cost worth knowing about: it forced the entire app out of static generation (`/` went from `○ Static` to `ƒ Dynamic` in the build output), since cookies are now read on every page via the root layout.

8. **Logout action.** `LogoutButton` client component calling `/api/auth/logout` then `router.push("/login")` + `router.refresh()`, wired into `SiteHeader` next to the "Dashboard" link when authenticated.

9. **Full verification pass.** Ran the complete flow against a freshly-provisioned Dockerized stack (fresh volume, fresh containers), matching the same from-a-clean-state rigor used on Days 1–3: register a new user → auto-login → land on `/dashboard` showing their name; cookie flags confirmed `httpOnly` + `SameSite=strict` present, `Secure` correctly absent (plain-HTTP local testing, by design per step 4); full regression sweep (refresh rotation, wrong password, duplicate email, logout, unauthenticated redirect) all still correct on the fresh state.

## Notable issues hit and resolved along the way

- **This isn't the shadcn/Next.js either of us might remember.** `apps/web/AGENTS.md` (bundled by `create-next-app`) explicitly warns this Next.js version has breaking changes from typical training data. That turned out to be true in two concrete ways used throughout the day: `middleware.ts` → `proxy.ts` (step 7), and shadcn's CLI now generates Base UI components instead of Radix (steps 1, 5). Both were confirmed by reading the actual bundled docs/source rather than assumed.
- **Two container startup bugs from the same root cause.** Both the Day 1 API image (documented in that day's summary) and this day's first `web` image independently hit the same failure mode: running a package-manager script (`pnpm start`) instead of the built binary directly triggers an unwanted network reinstall on every container start. Worth remembering as a pattern for any future service Dockerfile in this repo.
- **A dependency-version mismatch, not a logic bug.** `@hookform/resolvers`'s `zodResolver` type-checked against an older Zod v4 internal version stamp than the installed `zod@4.4.3` — a build failure with a runtime-looking error. Resolved via the officially documented `standardSchemaResolver` rather than pinning Zod to an older version.
- **The `Secure` cookie flag needed to be request-derived, not environment-derived.** Since the Docker image sets `NODE_ENV=production`, a common `secure: process.env.NODE_ENV === 'production'` pattern would have set `Secure: true` even for local `docker compose up` testing over plain HTTP — which Chrome silently refuses to store. Caught during design, before it could break step 9's verification.
- **The Browser pane preview tool became unreliable for the final two steps** (`navigation ... denied or failed` across multiple tabs, with no corresponding server-side errors in `docker logs`) — an environment issue, not app code. Fell back to curl-based HTTP-level verification (status codes, `Set-Cookie` headers, redirect locations, response bodies), which is reliable but doesn't literally confirm pixels rendered; flagged this explicitly rather than silently substituting it as equivalent.

## End state

Register, login, session-aware navigation, protected routes, silent access-token refresh, and logout all work end-to-end through the Next.js BFF against the Dockerized NestJS API — with the browser never handling a raw JWT at any point. The full stack (`postgres` + `api` + `web`) comes up together via `docker compose up`, matching the Day 4 acceptance criteria in the design doc.
