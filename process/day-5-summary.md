# Day 5 — Frontend tasks UI: Summary

Status: Complete. All 8 build steps plus verification from `plans/day-5-frontend-tasks-ui.md` executed and verified, plus one follow-on feature (inline tag deletion) added after user testing surfaced a gap in the original plan.

## What was done

1. **BFF proxy routes for tasks/tags.** `/api/tasks`, `/api/tasks/:id`, `/api/tags`, `/api/tags/:id` forward to NestJS with the access-token cookie attached as a Bearer header. The refresh-and-retry logic Day 4 built into `/api/auth/me` (silent refresh on a 401, one retry, re-set cookies) is shared across all eight of these endpoints via a single `proxyAuthedRequest()` helper in `lib/backend.ts`, rather than reimplemented per route.

2. **TanStack Query wired in.** `lib/query-client.ts` follows the standard SSR-safe App Router pattern: a fresh `QueryClient` per request on the server, a browser singleton that survives client-side navigation. `QueryProvider` wraps the root layout.

3. **Task list page.** `TaskList` fetches via `useQuery` against the BFF, rendering each task with a status badge (gray/blue/green, checkmark + strikethrough for done), a priority dot (gray/amber/red), a due-date badge that turns amber within 24h and red if overdue, and tag chips — per the design doc's visual language.

4. **Create task flow.** A dialog form (`react-hook-form` + Zod, `standardSchemaResolver`, matching Day 4's established pattern — no bundled `Form` component in this shadcn generation) for title, description, status, priority, due date, and tags, submitting via the BFF and invalidating the task list query on success.

5. **Edit task flow.** The create dialog was refactored into a single shared `TaskFormDialog` that takes an optional `task` prop — omit it to create, pass a task to edit (pre-populated, submits `PATCH`). Reused rather than duplicated, per the plan's own wording ("same form pre-populated with existing values").

6. **Delete with confirmation.** A focused confirmation dialog (task title shown for context, red destructive "Delete" button, "Cancel" as the safe default) wired to a hover-revealed trash icon on each task row.

7. **Filtering/sorting/search UI.** Search (debounced), status filter, priority filter, tag filter, and a combined sort dropdown (newest/oldest/due date/priority/title) — all reflected in the URL's query string via `useSearchParams`/`router.replace`, which both `TaskFilterBar` and `TaskList` read as the single source of truth. Distinguishes "no tasks yet" from "no tasks match your filters" (with a "Clear filters" action) per the design doc.

8. **Inline tag creation in the task form.** A small input + "Add tag" button beneath the tag chips; creating a tag appends it straight into the query cache (no refetch wait) and auto-selects it for the task being edited.

9. **Full verification pass.** Registered a fresh user against a freshly-rebuilt Dockerized stack and exercised full CRUD, every filter/sort/search combination, and cross-user isolation via curl (see "Notable issues" below for why curl rather than the browser).

## Follow-on: inline tag deletion (not in the original plan)

User testing after step 8 surfaced a real gap: tags could be created inline but never deleted, so a testing session's throwaway tags just accumulated and cluttered the form. The design doc actually specifies a "Tag management" screen (list tags, delete with confirmation, warn if in use) as its own numbered screen — but neither the Day 5 nor Day 6 plan ever scheduled a step to build it (Day 6 only tests "deleting a tag that's in use" as a manual-pass edge case, assuming the capability already exists). Asked the user where it should live rather than guessing; they chose inline-in-the-form over a separate management dialog. Implemented as a small `×` on each tag chip that swaps that chip into an inline "Delete 'x'? Yes/No" confirmation — avoiding a dialog nested inside the already-open task dialog. Verified via curl that deleting an in-use tag cascades correctly: the tag disappears, but the tasks that referenced it survive untouched (Prisma's `onDelete: Cascade` on `TaskTag`, not `Task`).

## Notable issues hit and resolved along the way

- **A real 500 bug: `<input type="date">` vs. Prisma's client.** The date input yields a bare `YYYY-MM-DD`, which passes the API's `class-validator` `@IsISO8601()` check but crashes Prisma 7's client (`Invalid value for argument dueDate: premature end of input`) — it requires a full ISO-8601 datetime. Caught via Docker logs during step 4 verification, not just a UI smoke test. Fixed by expanding to midnight UTC (`new Date(value).toISOString()`) before sending.
- **Two new React Compiler ESLint rules, not present in earlier days.** `react-hooks/purity` (rejected a direct `Date.now()` call in `DueDate`'s render body — fixed with a lazy `useState(() => Date.now())` initializer, the sanctioned one-time-impure-read location) and `react-hooks/set-state-in-effect` (rejected re-syncing the edit form via a `useEffect` — fixed with React's "key resets state" pattern, remounting the form component keyed by `open`+`task.id` instead). Both apply generally to this Next.js/React version, not just this feature.
- **A dialog-backdrop rendering bug, diagnosed from a user report.** The user saw a black box flash when opening the status/priority selects or the due-date picker from inside the create/edit dialog. First guess (a missing `color-scheme` CSS property) was wrong — the actual cause was `backdrop-blur-xs` on the dialog's overlay, which triggers a known Chromium compositing bug where native `<select>`/`<input type="date">` popups paint solid black near a `backdrop-filter` ancestor. Removed the blur; kept the plain translucent scrim. The `color-scheme` declaration was still added (a correct, independent hardening) but wasn't the actual fix — worth remembering that root-causing sometimes takes two tries even with a clear symptom description.
- **A cross-user data leak in the UI, caught by the user, not by testing.** Logging out and back in as a different account in the same tab kept showing the previous account's tasks until a full page reload. Root cause: `getQueryClient()`'s browser singleton (intentional, for cache survival across client-side navigation) also survives a logout→login identity switch, and neither `LogoutButton` nor the login/register forms ever cleared it — `router.refresh()` only re-runs Server Components, not the TanStack Query cache. Fixed with `queryClient.clear()` in all three (logout definitively, login/register defensively for the case of an expired session with no explicit logout).
- **A second-order bug from fixing the first one.** After wiring "Clear filters" to reset the URL query string, the search input's own local (debounced) state didn't re-sync, since nothing told it the URL had changed for a reason other than its own debounce commit. Fixed with React's "adjust state during render" pattern (compare the URL's current value against a tracked "last synced" value each render, correcting only on a real external change) — deliberately not a `useEffect`, to avoid reintroducing the `set-state-in-effect` issue from above, and deliberately not the "key" trick either, since remounting on every debounce commit would have dropped focus out of the input mid-typing.
- **A deliberate, flagged deviation from the design doc.** The design prompt calls for a tag filter as "multi-select chips," but the backend's `GET /tasks` only ever accepts a single `tagId` (`QueryTasksDto`, unchanged since Day 3). Building a multi-select that silently only filtered by one tag would have been misleading, so it was built as a single-select instead, with the mismatch called out to the user rather than worked around silently.
- **The Browser pane preview tool was unreliable for nearly this entire day** (`navigation ... denied or failed` / empty pages, across dozens of attempts, multiple full restarts, and fresh tabs) — confirmed as an environment issue, not app code, since the user's own browser worked throughout and could confirm fixes (the backdrop-blur black box, the query-cache leak) that this session's tooling couldn't see. Fell back to curl-based verification of every API-observable behavior throughout, and was explicit each time about what remained visually unconfirmed rather than claiming a UI check that didn't happen.

## End state

Full task CRUD, filtering, sorting, search, and inline tag creation/deletion all work end-to-end through the Next.js BFF against the Dockerized NestJS API, verified via a clean-state curl walkthrough (fresh user, fresh containers) covering create/read/update/delete, every filter and sort combination, cross-user isolation, and cascade-safe tag deletion. `tsc`, `eslint`, and `next build` are clean across every step. One capability gap remains flagged but unresolved: true multi-tag filtering would require a backend change (`GET /tasks` accepting a list of `tagId`s) that was out of scope for Day 5.
