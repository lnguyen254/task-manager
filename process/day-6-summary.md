4. **Session-expired handling.** Added an `ApiError` class (carries the HTTP status) that `lib/tasks.ts`/`lib/tags.ts` now throw instead of a plain `Error`, so a 401 can be told apart from other failures. `lib/query-client.ts` registers a `QueryCache`/`MutationCache` `onError` handler: on a 401, it clears the query cache and hard-redirects to `/login?sessionExpired=1`. The login page reads that param server-side and shows "Your session has expired. Please log in again." instead of the session just failing silently.

5. **Responsive layout pass.**
   - `TaskFilterBar`: the five inline controls (search/status/priority/tag/sort) collapse into a single "Filters" button + right-side sheet below `lg` (desktop keeps the full inline row), reusing one JSX block for both layouts rather than duplicating the controls.

   - Verified (not changed): login/register cards already fit cleanly at every width.
   - All three breakpoints (390px / 820px / 1400px) confirmed live in the browser before the browser was taken out of scope for the rest of the day.

6. **Backend security hardening pass.**
   - **Helmet**, with CSP explicitly disabled — Nest's own documented workaround, since Helmet's default CSP blocks Swagger UI's inline bootstrap script at `/api/docs`. Every other header (HSTS, frame-guard, etc.) stays on.
   - **`@nestjs/throttler`**: global default 100 req/min; `AuthController` tightened to 10 req/min (curl-confirmed: the 11th rapid login attempt gets a 429); `HealthController` exempted via `@SkipThrottle()`; the guard itself is conditionally left out of `AppModule`'s providers when `NODE_ENV === 'test'`, since Jest sets that automatically and e2e specs reuse one app instance across many `it()`s — without the exemption, rate limiting would have made the existing e2e suite flaky rather than testing anything real.
   - **CORS** locked to a new `CORS_ORIGIN` env var (default `http://localhost:3001`), added to `.env.example` and `docker-compose.yml`.
   - **`AllExceptionsFilter`** (new, global): normalizes every response to `{statusCode, message, error}`. Nest's built-in `HttpException` subclasses already produce this shape and pass through unchanged; anything else (a bug, a driver error) collapses to a generic 500 so its message/stack never reaches the client — the real error is logged server-side instead. Unit-tested directly (mocked `ArgumentsHost`) rather than only through e2e, since it's pure logic.
   - **Zod env validation at boot** (`validateEnv()` in `src/config/env.ts`, called at the top of `main.ts`'s `bootstrap()` before `NestFactory.create`): fails fast with a readable per-field error list on missing/malformed config, confirmed live by booting the container with a too-short JWT secret.

7. **Manual full-stack test pass**, done entirely via curl against the Dockerized stack (through the Next.js BFF, using a cookie jar to reproduce real cookie-based session flow) after browser tooling was ruled out for the rest of the day. Covered:
   - **Golden path**: register (auto-logs in) → login → create three tasks (with a tag, a due date, mixed priorities) → edit two of them → every filter/sort combination (status, priority, tag, search, title-sort) → delete → logout → confirmed the session is actually gone afterward.
   - **Edge cases**: invalid input on register/login/task-create (bad email, short password, missing name, empty title, invalid status enum, malformed due date); duplicate email and duplicate tag name (both 409); no session and garbage session cookies (401 + cookies cleared); cross-user task access (404, not 403 — doesn't confirm the resource exists to the wrong user); refresh token rotation plus reuse-of-a-rotated-token rejection; empty task list vs. empty-after-filtering (same `{data:[],total:0}` API shape in both cases, confirming the differentiated copy is correctly a frontend-only decision); deleting an in-use tag (tag gone, the two tasks that referenced it survive with an empty `tags` array).

## Notable issues hit and resolved along the way

- **A real bug caught by the curl verification in step 6, not by the unit tests.** `AllExceptionsFilter`'s fallback for a *parameterless* exception (e.g. `AuthGuard`'s default `new UnauthorizedException()`, which has no `error` key in its own response body) used `exception.name` — the JS class name (`"UnauthorizedException"`) — instead of the correct HTTP reason phrase (`"Unauthorized"`). Only surfaced by actually hitting a protected route with no token and reading the raw JSON; fixed by deriving the phrase from Node's built-in `http.STATUS_CODES[status]` instead, with a regression test added before moving on.
- **No frontend test framework exists in this repo** (no Jest/Vitest/RTL in `apps/web`), unlike the backend which has Jest set up from Day 1. Asked the user how to handle this before starting step 1 rather than silently introducing a new framework or silently skipping TDD; the answer was to match the existing convention (Days 4–5): no unit tests, verify via `tsc`/`eslint`/`next build` plus a manual pass. Backend work, by contrast, did follow TDD throughout (env validation and the exception filter were both written test-first) since Jest was already there.
- **`jest.fn()` generic typing gotcha.** `@types/jest@30` still uses the older three-generic form (`jest.fn<ReturnType, ArgsTuple>()`), not the newer single-function-type form (`jest.fn<(args) => Return>()`) — using the latter silently produced an `any`-typed mock and two ESLint `no-unsafe-*` errors that only made sense once traced back to the wrong generic shape.
- **Docker startup timing, not a code bug.** Early in the day, `docker compose up --build` hung with zero output because Docker Desktop's daemon wasn't actually running yet when the command was issued (a Windows named-pipe connection just blocks silently rather than erroring). Separately, immediately after Docker Desktop was started, the very next build hit `ENETUNREACH` on every `pnpm install` registry request from inside the build container — Docker Desktop's internal network stack was still finishing initialization for a few seconds even though the daemon API was already responding. Both resolved by retrying once the daemon/network had actually finished starting; confirmed via `docker run` reaching the registry successfully before retrying the real build.
- **A pre-existing, unrelated `tsc` error** in `auth.service.spec.ts` (a mock `User` object missing the now-required `createdAt` field) was blocking a clean type-check baseline for verifying this day's own changes. Fixed with a one-line addition since it was clearly pre-existing (confirmed via `git diff` showing no prior changes to that file) and needed to trust `tsc`'s output going forward.
- **Pre-existing CRLF/Prettier lint noise** in several untouched backend files (`tags.controller.ts`, `tasks.controller.ts`, `tags.service.spec.ts`, `tasks.service.spec.ts`, `tasks.service.ts`) was left alone — confirmed unrelated to this day's work and out of scope to fix incidentally.
- **A deliberate scope boundary drawn mid-day**: the user asked partway through step 1 to stop using browser automation for the rest of the session. Step 2's responsive work had already been visually confirmed at all three breakpoints before that point; step 4's manual pass was then done entirely through curl against the BFF instead of the browser. The one plan item this couldn't close out — confirming no browser console errors during the manual pass — is flagged as an open item rather than silently claimed as done.
